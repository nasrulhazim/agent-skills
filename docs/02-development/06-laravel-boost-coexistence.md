# Coexisting with Laravel Boost

Laravel Boost ships its own Claude Code skills and installs them into the **same directory**
this toolkit installs into. A name shared between the two is not a merge — it is an
overwrite, and nothing reports it.

## What Boost owns

`php artisan boost:install --skills` writes these into a project's `.claude/skills/`:

| Skill | Covers |
|---|---|
| `pest-testing` | Pest 4 syntax, datasets, browser testing, `arch()` |
| `laravel-best-practices` | Eloquent, caching, queues, validation, security defaults |
| `livewire-development` | Livewire 4, `wire:` directives, SFC/MFC, v3→v4 migration |
| `fluxui-development` | `<flux:*>` components, composition, theming |
| `tailwindcss-development` | Tailwind v4 utilities, CSS-first config |
| `configuring-horizon` | Supervisors, balancing, dashboard auth, notifications |

They carry `license: MIT` and `metadata.author: laravel` in their frontmatter — that is the
reliable way to tell one apart from a toolkit skill. They are **regenerated by Boost**, so any
local edit is lost on the next `boost:install`.

## The collision, and how it presented

Kickoff bundles toolkit skills into `stubs/.claude/skills/` and copies them during scaffolding.
`boost:install` runs **after** that copy. Both write `.claude/skills/<name>/`.

In a live product this meant Boost's `pest-testing` had replaced Kickoff's — same path,
different content, no warning. The Kickoff skill's scaffolding patterns, Spatie Permission
helpers and arch-test baseline were simply gone, and the loss was only found by diffing the
two trees months later.

## The rule

**Never ship a toolkit skill under a name Boost owns.** Copy order is not a strategy — it
depends on when a user last ran `boost:install`.

- The toolkit's Pest skill is therefore named **`kickoff-pest-testing`**.
  `migrations.txt` carries `skills/pest-testing:skills/kickoff-pest-testing`, so
  `install.sh` cleans up the old `~/.claude/skills/pest-testing` on the next run. The
  installer only ever touches `$HOME`, so a project-level skill written by Boost is never
  removed by a migration.
- Kickoff's `bin/sync-claude-assets` fails loudly if its `STUBS_SKILLS` list ever names
  something on Boost's list. Add to `BOOST_OWNED_SKILLS` there when Boost ships a new skill.

## Do not fork Boost's skills

They track the framework and are maintained upstream. If Boost's coverage of a topic is
adequate, ship nothing — a stale fork is worse than a dependency. Write a toolkit skill only
where it adds something Boost does not have, and give it a name that says so:

| Boost skill | Complementary toolkit skill | What the toolkit adds |
|---|---|---|
| `pest-testing` | `kickoff-pest-testing` | Scaffolding from detected classes, Kickoff arch-test baseline, suite performance (seeder placement, Xdebug/pcov, TIA) |
| `fluxui-development` | `livewire-flux` | Kickoff component patterns — form modal vs flyout, data tables, Spatie Media Library uploads, the client-side gotchas |
| `laravel-best-practices` | `project-laravel` | Kickoff conventions specifically: `Base` model, attribute syntax, dual keys, modular routes, tenancy scoping |

Both load together. They are not competing for the same question.

## Checking a project

```bash
# Which skills came from Boost?
grep -l 'author: laravel' .claude/skills/*/SKILL.md

# Any name present in both sets?
comm -12 \
  <(ls ~/.claude/skills | sort) \
  <(grep -l 'author: laravel' .claude/skills/*/SKILL.md | xargs -n1 dirname | xargs -n1 basename | sort)
```

A non-empty second result means a toolkit skill is being overwritten in that project. Rename
the toolkit skill; do not delete Boost's.
